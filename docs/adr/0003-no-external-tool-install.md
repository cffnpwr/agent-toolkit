# primitiveは外部ツールを導入せず、依存パッケージの同期にとどめる

primitiveは、実行に使う外部ツール(bun・uv・jj・gh等の実行ファイル)を自身で導入しない。
同梱したロックファイルにバージョンが記録されている依存パッケージだけを、使用前に同期する。
primitiveは[APMが配布する最小単位](https://microsoft.github.io/apm/concepts/glossary/#primitive)。
harnessは[primitiveを実行するagent runtime](https://microsoft.github.io/apm/concepts/glossary/#harness)。

## Context

APMはprimitiveのファイルを各harnessへ配置するが、実行時に必要となるものを導入する仕組みを持たない([ADR 0001](./0001-adopt-apm.md))。

primitiveの外部依存は2種に分かれる。

- 依存パッケージ: プログラミング言語のパッケージマネージャで導入するライブラリ。
  定義ファイルとロックファイルを同梱できる
- 外部ツール: CLI・インタプリタ・パッケージマネージャ本体など、プログラミング言語のパッケージマネージャでは導入しない実行ファイル

実行時に依存が満たされていない場合、primitiveが自分で導入するかどうかを決める必要がある。

## Choices

1. 外部ツールは存在確認のみ行い、依存パッケージをロックファイルから同期する
2. primitive自身が外部ツールも導入する

### 1. 外部ツールは存在確認のみ行い、依存パッケージをロックファイルから同期する

外部ツールの不在は検知するだけで、導入しない。
依存パッケージは、同梱した定義ファイルとロックファイルから使用前に同期する。

#### Pros

- 外部ツールの入手経路をprimitiveが持たずに済む
- 同期の変更が`node_modules`・`.venv`に閉じる
- インストールされるバージョンをロックファイルが固定するため、primitiveが宣言するバージョンと実行時のバージョンが一致する

#### Cons

- 外部ツールの導入を、このパッケージを使う環境に要求する
- 外部ツールが不在の環境では、primitiveが機能しない

### 2. primitive自身が外部ツールも導入する

外部ツールの不在を検知したとき、primitiveがその導入まで行う。
導入先はprimitiveの配下にも、PATHの通った共通の場所にも置ける。

#### Pros

- 外部ツールの導入を環境に要求せず、配置した直後から動く

#### Cons

- primitiveが、対応するOS・アーキテクチャの組み合わせごとに、入手経路と検証手段を持つことになる
- 実行ファイルが動的リンクで要求する共有ライブラリ(`lib*.so`等。[ld.so(8)](https://man7.org/linux/man-pages/man8/ld.so.8.html))を環境ごとに確認する
- 導入したツールのバージョンを固定する仕組みがなく、primitiveが宣言するバージョンと実行時のバージョンが一致しない
- 導入先をPATHの通った共通の場所に置く実装では、変更が他のprimitiveや利用者の環境へ及ぶ

## Decision

選択肢1を採る。

外部ツールを導入するには、対応するOS・アーキテクチャの組み合わせごとの入手経路と、実行ファイルが要求する共有ライブラリの充足を、primitiveが引き受けることになる。
bunを例に取ると、この組み合わせを網羅する作業がprimitiveの責務を超える。

依存パッケージの同期はこれに当たらない。
ロックファイルがインストールされるバージョンを固定するため、primitiveが宣言するバージョンと実行時のバージョンが一致し、変更も`node_modules`・`.venv`に閉じる。

## Consequences

- 外部ツールの導入は、このパッケージを使う環境の責務になる
- 外部ツールが不在のときの振る舞いは、スキル・hookそれぞれの設計で定める
- 依存の追加・更新(`bun add`・`uv add`等)は、primitiveの実行時に行わない
- 各primitiveは、自身が使う外部ツールと依存パッケージを宣言する
