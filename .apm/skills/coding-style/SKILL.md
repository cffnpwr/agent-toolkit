# Coding Style

## 使い方

1. 対象コードと依頼から言語を判定する
2. 該当するreferenceを読む
   - [Rust](references/rust.md)
   - [Go](references/go.md)
   - [TypeScript](references/typescript.md)
   - 上記以外の言語は本文のルールだけを適用し、言語固有の書き方は対象言語の慣行に従う
3. 本文のルールと、referenceの言語固有の書き方を合わせてコードを書く

## ルール

特別に記載がない場合、言語固有のルールは以下に列挙する共通のルールより優先して扱う。

### 構成

- 使用しない型・構造体・クラス・関数・ファイル・ディレクトリを追加しない
  - 将来の再利用・対称性・見た目の整理を理由に作らない
  - `.gitkeep`のように存在することに意味がある場合は例外とする
- 誤った共通化をしない
  - 年齢のバリデーションと数量のバリデーションはどちらも非負整数であることを検証する処理が必要だが、これは重複ではない
  - 誤った抽象化よりも重複を許容する
  - まったく同じコードが同じ背景・目的で3箇所以上存在する場合は共通化を検討する
- 型・変数・構造体・クラス・関数等のスコープはそれが必要な最小限のスコープにする
  - 何でもpublicな型・変数・構造体・クラス・関数にしない
- 1ファイルの実装はおよそ200行を目安に抑え、超えるなら分割する
  - In-Source testing等でテストと実装が同じファイルに存在する場合は実装部分のみを対象として計測する
- ファイル内は、上から次の順に書く
  1. import
  2. 定数の定義。言語の制約で定数として定義できない値も、定数として扱うならここに書く
  3. 型・インターフェイス・トレイトの定義
  4. その他
- ディレクトリは責務・抽象度ごとに階層を分ける
  - 責務・抽象度の異なるファイルを同じディレクトリに並べない
  - 例: 外部ツールの実行・LLMの呼び出し・それらを組み合わせる処理のファイルを、同じディレクトリに並べない

### 型

- 位置によって値の意味が変わる配列・タプルを使用しない
  - 複数の値をまとめて扱いたい場合（複数の値を返す関数の返り値等）はオブジェクト・構造体等の名前や型で値の意味を説明できる形式にする
  - Reactの`useState`の返り値等の慣習として定着しているものは例外とする
- 意味のないアクセサメソッドを作らない
  - 原則として型でimmutabilityを表現する
  - 型によるimmutabilityの表現が不可能な場合など特殊な場合は例外とする
- 一意に推論できる型は明示しない
  - 型推論により推論される型を明示的に書かない
  - 関数の戻り値の型は、推論に任せず意図して定義するものなので明示する

### 検証

- 外部入力（ファイル・CLI引数・環境変数）は早期に検証する
  - 入力値検証は入力を受け取った箇所で行なう
    - 内部の実装（DB・外部API等）が拒否することを検証の代わりにしない
    - 内部の実装でしか判定できない妥当性（存在確認等）は内部の実装の責務
  - 成立している前提へのfallback・nullチェック・入力値の検証をしない
    - 前提が破れたらpanic・例外で終了する
- 制約は型・バリデーション等で担保する
  - 手書きの検査コード・規約コメント・`never`ハックで代替しない
  - 分岐の網羅は、exhaustive検査ができる言語機構やライブラリを使用する
    - 到達不能な分岐は`unreachable!`・panic相当で明示する
  - 取りうる値が列挙可能な場合は列挙型を使用する

### エラーハンドリング

- 異なる抽象度で同じエラーを共有しない
  - 同じ意味のエラーであっても流用せずにカプセル化する
- 失敗時のリトライ処理を書く場合は目的にあった適切なインターバルを設定する
  - `Retry-After`ヘッダーが存在すればその値を使う
  - 指数バックオフ方式を使用する
- 検証・エラーメッセージは何が発生したか・何がどう不正か・許容される値・条件を事実として示す
  - 命令形の指示（「〜してください」）を書かない

### 値

- マジックナンバー・リテラルを置かない
  - 値には名前を与えるか、その値である根拠を辿れる形にする
  - 自明なリテラル（0・1・空文字列・出力文字列等）はそのまま書いてよい
- 呼び出しのたびに同じ値を返すだけの関数は定数にする

### 外部依存

- 外部依存のバージョンは、内容が変わらない識別子で固定する
  - 可変タグを参照しない
    - OCI Imageのバージョンはハッシュ値で固定する
      - 正: `hogehoge:v1.2.3@sha256:01234356789abcdef`・`hogehoge@sha256:01234356789abcdef`
      - 誤: `hogehoge`・`hogehoge:latest`・`hogehoge:v1`・`hogehoge:v1.2.3`
    - その他パッケージマネージャーではバージョンを固定値にする
      - 使用するパッケージマネージャーのバージョン固定方法に従って適切に指定する
      - 正: `1.2.3`・`==1.2.3`・`=1.2.3`
      - 誤: `>=1`・`~>1, <2`・`*`・`latest`
- 明示的な指示がない限り車輪の再発明を避ける
  - 検証ロジックを自作せず、スキーマ検証ライブラリを使う

### 用語

- 語彙は対象分野の一次ソース（公式リファレンス・仕様書）が使う語に合わせる
  - 専門用語は、その分野での定義どおりに使う
  - 妥当性を判断できない語は、一次ソースの呼び方を確認してから決める
  - 造語を使用しない
  - 内部表現の単位・内部の識別子をそのまま出さない

### 命名規則

- 使用する言語での慣習がある場合は優先して従う
- 形容詞（-ed・-ingも可）+名詞
  - 変数の一般的な命名方法
  - `validatingPolicy`
  - `createdItems`
  - `errorCode`などの名詞のみで的確に内容を表せる場合は例外
  - 関数の引数としての`target`等のその位置や役割から内容を的確に表せる場合は例外
  - for文のループカウンタや一時的な代入など、スコープが狭く限られている場合は例外
- -on・-at
  - 日付・日時を表す場合
  - 特定の瞬間を表す場合は`at`・幅がある場合は`on`
  - `deletedAt`（削除された日時）
  - `updatedOn`（更新された日付）
- is-・has-・contains-
  - Bool値の場合
  - has・containsは持つ・含むを表現する場合に使用
  - `isActive`
  - `hasAdminPermission`
  - `containsHogeValue`
- on-
  - イベントの場合
  - `onClicked`
  - `onReceived`
- to-
  - 何かを変換する場合
  - `toString`
  - `toInt`
- 動詞+目的語
  - 関数の一般的な命名方法
  - メソッドチェーンなどの場合は対象が明確なため`map`・`flatten`等の動詞のみの命名をしてよい
  - `createTmpFile`
  - `toggleStatus`
- 名前は対象と条件を過不足なく表す
  - 「候補」「対象」のような曖昧語を、実際に適用している条件に置き換える
- 名前と型を一致させる
- 単数・複数を意識する
  - 不加算名詞を避ける

### コメント

- 実装上の制約・実装する際に確認した資料への参照等のコメントを書かない
- 書いた後に削れる語を探し、意味が変わらなければ削る
- ファイルの先頭にそのファイルには何が書かれていて何が実装されているか・実装上の制約・実装する際に確認した資料への参照等のコメントを書かない
  - それを書かなければいけないのであればファイルの配置が不適切であるため、ファイルの配置を見直す
- コメントは基本的に1行（80文字以内）で書く。固有名詞が長い等の回避不可能な場合は例外
  - 1行のコメントでは必ず`//`・`#`を使用する
- JSDoc等のドキュメンテーションコメントは基本的に書かない
  - その関数・変数・定数等が何のために書かれていて何をするものなのか・引数や戻り値の意味は関数名・変数名・定数名・型で表現する
  - ユーザーが明示的に指示をした場合は例外
- 理由を長々と書かない。「○○のため、××する」程度にする。3段階以上の因果関係を書かない
- コードを読めば自明なことは書かない
- コードから読み取れることをコメントに書かない
- WHAT・HOWは不要ならば書かない
- コメントは、内容が指す対象の直前に書く
  - 分岐・条件・フィールド・引数を説明するコメントは、それを含む関数・型の宣言ではなく、その分岐・条件・フィールド・引数の直前に置く
- 識別子の言い換えは書かない
- 非口語・体言止めで書く
- 文末に句点「。」・ピリオド「.」をつけない
  - 言語ごとの慣習よりも優先する
- 比喩的・詩的表現を使用しない。技術的事実をそのまま記述する
- 区切りのためのコメントを書かず、まとまりは空行で示す
- 処理の流れや区分を説明するコメントが必要になるほど長い関数・ファイルは、コメントを足さずに分割する
- ユーザーが「○○は使わない」「○○は不要」「○○は禁止」などの否定的な要件を指定した場合に「○○不使用」「○○なしで実現」「○○を使っていません」など、要件遵守をコメントに書かない
  - ユーザーが説明の追加を明示的に指示した場合は例外とする
  - 禁止された要素の代わりに採用した技術や設計を宣伝しない
- まだ存在しない要求を、現在の実装の根拠として書かない
