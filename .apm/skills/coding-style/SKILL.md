# Coding Style

コードを書くときの規約を、言語非依存の原則と、分野別の表現、言語別の書き方に分けて示す。

## 概要

原則は設計判断にまで使う方針で、表現は場面ごとの具体的な書き方である。

実コードがこの文書と食い違ったら、この文書を正とする。

lint・format・hookが機械判定する項目はこの文書に書かず、そちらの判定に従う。

## 最初にすること

1. 対象コードと依頼から言語を判定する
2. 該当するreferenceを読む
   - Rust → [references/rust.md](references/rust.md)
   - TypeScript → [references/typescript.md](references/typescript.md)
   - Go → [references/go.md](references/go.md)
   - 一覧に無い言語 → referenceは無い。
     本文の原則と表現だけを適用し、言語固有の書き方は対象言語の慣行に従う
3. 本文の原則・表現と、referenceの言語固有の書き方を合わせて適用する

## 原則（言語非依存の核）

### 設計判断

- **現状の構成を出発点にしない。**「本来どうあるべきか」で決める。
  現状に合わせる場合は、その妥協を選んだ理由を示す
- **手段が目的をどれだけ前進させるかを述べられない場合は採らない。** 導入に要る準備・前提が、解決する問題より大きい手段も採らない
- **要素を足すときは、それが無い場合と比べて何が変わるかを述べる。** 述べられない要素（パラメーター・フィールド・中間リソース・ヘルパー・制御機構）は入れない
- **責務の境界を先に決め、変更はその境界の内側に置く。** 他の層・他のリポジトリが責務を持つものを、手近だという理由で自分の側に置かない
- **同じものを二か所に書かない。** 制約・定義・設定を複数の層に重複させると、片方を変えたときに整合が取れなくなる
- **実装側の都合を利用者側のインタフェースに出さない。** 内部の制限は内部で吸収する
- **既存の同種の実装・設定に合わせる。** 同じ問題を扱う箇所を先に探し、その書き方を踏襲する。
  新しい書き方を持ち込む場合は理由を示す
- **汎用の成果物に、特定のAI Agent製品や実行基盤を前提とした記述を焼き込まない。** 製品名・その固有機能・その設定ファイルへの依存が対象である

### 構造

**構造は、それがないと今のコードが書けないときだけ作る。** 対象は名前付き型・共通関数・基底クラス・新ファイル・パラメーター構造体である。
将来の再利用・対称性・見た目の整理を理由に作らない。

- **意味が位置から読めない多重配列・タプルで渡さない。** 意味はオブジェクトのキー・構造体フィールドの名前で示す
- **同じ目的・同じ責務のコードは共通化する。** 形が似ているだけで目的が違うものは共通化しない
- **型は、それを使う主体が1つのファイルにあるなら、そのファイルに定義する。** 複数のファイルで横断的に使う型は型定義ファイルに置く。
  1つのファイル内でしか使わない型のために型定義ファイルを作らない
- **エラー型は投げるモジュール内に定義し、層をまたいで共有しない。** 同じ意味に見えるエラーでも、層が違えば別の型にする
- **1ファイルの実装はおよそ200行を目安に抑える。** 超えるなら分割する
- **ファイルは扱う対象（機能・データ）ごとに分け、種類（テスト種別・処理の段階）ごとに分けない。** 種類で分けると、1つの対象への変更が複数のファイルに散る
- **役割の異なるファイル群ができたらディレクトリで分ける。** ディレクトリを作るかどうかも、それがないと書けないかで判断する
- **検証や制約は、それが掛かるフィールド・関数のそばに書く。** 定義の先頭にまとめて書くと、対象と制約の対応が追えなくなる
- **新しいファイルを作るのは、新しい型を導入するときと、200行を超えたファイルを分割するときだけとする。** 既存の型・機能への追加は既存のファイルへ追記する

### 入力と境界

**外部入力は防御的に、内側は攻撃的に書く。**

- **外部入力（ファイル・CLI引数・環境変数）は入口でスキーマ検証する。** 検証ロジックを自作せず、スキーマ検証ライブラリを使う
- **許可リストか拒否リストかは、その制約をどちらで正確に表現できるかで決める。**
- **入力の形式・範囲の検証は、入力を受け取った層で行う。** 下流（DB・外部API）が拒否することを検証の代わりにしない。
  下流でしか判定できない妥当性（存在確認等）は下流の責務のままにする
- **異常系の挙動を実装前に定義する。** 壊れた入力・欠けた入力で何が起きるかを決めてから書く
- **必要な権限・能力だけを要求する。** 要求する各権限の理由を説明できるようにし、必要な権限・前提はヘルプとドキュメントに書く
- **CLIは標準入力からの入力を受け付ける。** とくに秘匿値を引数で渡させない
- **境界の内側では検証済みの値を素のまま使う。** 成立している前提へのfallback・nullチェック・防御コードを書かない。
  前提が破れたらpanic・例外で落ちてよい

### 検査

**制約は、機械が検査できる形にする。** 手書きの検査コード・規約コメント・`never`ハックで代替しない。

- **取りうる値の集合は型で閉じる。** ユニオン型・`enum`で、それ以外の値が入らないことを型に強制させる
- **分岐の網羅は、exhaustive検査ができる言語機構やライブラリに任せる。**
- **外部入力の形は、スキーマ検証ライブラリに検査させる。**
- **この閉じ込めが成立しているから、境界の内側で防御コードが不要になる。**

## 表現

場面ごとの具体的な書き方。

### 言語共通

- **比較は完全一致を既定とする。** 部分一致・緩い比較にするなら理由が要る
- **到達不能な分岐は`unreachable!`・panic相当で明示する。**
- **待ちには必ず上限を設ける。** 終了条件だけを持つループを書かない
- **リトライは指数バックオフにする。** 固定間隔での再試行を繰り返さない
- **実行環境に存在する前提を確認する。** 手元のコマンド・資源・並列度が実行先にもあるとは仮定しない
- **読ませるだけのフィールドは公開し、`getter`を書かない。** 不変条件を守るフィールドだけ非公開にする
- **ビルダーは消費型にし、メソッドチェーンで組み立てる。** 自身を受け取り、自身（または自身を含む結果型）を返す
- **一意に推論できる型は明示しない。**

### 命名

- **語彙は対象分野の一次ソース（公式リファレンス・仕様書）が使う語に合わせる。** 妥当性を判断できない語は、一次ソースの呼び方を確認してから決める
- **造語を作らない。** 既存の英語表現を独自に訳した語、分野で通用しない語を使わない
- **分野の専門用語は、その分野での定義どおりに使う。** 近い概念に流用しない
- **名前は対象と条件を過不足なく表す。**「候補」「対象」のような曖昧語を、実際に適用している条件に置き換える
- **名前と実体を一致させる。** ファイル名・テスト名は、その中身が何であるかを示す

### 値

- **根拠を説明できない値（マジックナンバー・仮の閾値）を置かない。** 値には名前を与えるか、その値である根拠を辿れる形にする。
  自明なリテラル（0・1・空文字列・出力文字列等）はそのまま書いてよい
- **呼び出しのたびに同じ値を返すだけの関数は定数にする。**
- **外部依存のバージョンは、内容が変わらない識別子で固定する。** 可変タグを参照しない

### コメント

- **実装から読み取れることを書かない。** 処理の言い換えを書かない
- **書くのは実装から読み取れないものに限る。** 設計判断の理由、選択肢の比較、外部の制約、値の根拠が対象である
- **まだ存在しない要求を、現在の実装の根拠として書かない。**
- **区切りのためのコメントを書かない。** 処理や宣言のまとまりは空行で示す
- **処理の流れや区分を説明するコメントが必要になるほど長い関数・ファイルは、コメントを足さずに分割する。**
- **ツールが再生成・除去する箇所に情報を置かない。**
- **実装コード・コメントからリポジトリ内のDesign Docを参照しない。** 配布物は設計文書を同梱しない

### 利用者に出る文言

- **利用者の語彙で書く。** 内部表現の単位・内部の識別子をそのまま出さない
- **利用者の言語で書き、文体を統一する。** 日本語話者向けなら日本語・敬体とし、不要な英語を混ぜない
- **検証・エラーメッセージは、何がどう不正かと、許容される値・条件を事実として示す。** 命令形の指示（「〜してください」）を書かない
- **ヘルプ・usageは、それだけで使い方が決まる情報を持たせる。** 名前の再掲だけの記述を置かない
