# Test Writing

## 使い方

1. 対象コードと依頼から言語を判定する
2. 該当するreferenceを読む
   - [Rust](references/rust.md)
   - [Go](references/go.md)
   - [TypeScript](references/typescript.md)
   - 上記以外の言語は本文のルールだけを適用し、言語固有の書き方は対象言語の慣行に従う
3. 本文のルールと、referenceの言語固有の書き方を合わせてテストを書く

## ルール

特別に記載がない場合、言語固有のルールは以下に列挙する共通のルールより優先して扱う。

### 粒度

テストピラミッドに従う。

- ユニットテストを最も多く書く
- integrationテストは要所に限定する
- e2eテストは最小限にする

### テスト対象

- publicな呼び出し経路はC1カバレッジを満たす
  - 到達不能な分岐（`unreachable!`・網羅した`match`のワイルドカード（`_`）アーム・実質的に発生しないエラー等）は対象外とする
  - 到達不能な分岐を通すために注入点・テストダブルを追加しない
  - 可能なら型の設計で分岐自体を不要にする
- 条件分岐やエラーハンドリングが必要な処理等のロジックを持つprivateな要素はテストする
  - 単純な委譲・受け渡しのみの要素は対象外とする
- 自明なコード（getter・引数をそのまま渡すラッパー等）はテストしない
- ネットワーク・DB・ファイルシステム等へのアクセスそのものはテストしない
  - アクセスの前後にあるロジックはアクセスから分離し、テストする
  - main関数等のエントリポイントのテストは追加しない。テストする必要性のあるエントリポイントが実装されている場合は指摘する
- 自分が実装していないもの（依存ライブラリ・ミドルウェアの機能等）はテストしない

### 副作用

テストで副作用を持つ処理（ファイル作成・外部コマンド実行・ネットワークアクセス等）を実行しない。

- 副作用を持つ処理は、引数・interface等で差し替え可能にする
- 引数解釈・組み立て・分岐のテストは、差し替え可能な箇所より手前の処理だけを実行する
- 副作用を持つ処理が未実装であることを、テストで副作用が発生しない根拠にしない

### Fixture

- テストの入力に実環境のファイル・本番の設定データを使用せず、fixtureを使用する
  - 実データでは代表・境界ケースを表現できない
  - 実データはテストと無関係な編集で変わり、そのたびにテストの結果が変わる
  - リポジトリにコミットされたデータも実データとして扱う
- 実データから代表的な形を生成してfixtureとする
- 実データを読み込めることの検証は、ユニットテストと分けて行なう
  - 実データを直接使用するテストは作らない
  - スキーマ検証等で実データと同じ形式のデータが読み込めることを確認する

### 再現性

確率的に失敗するテストを書かない。
外部要因で失敗した場合は失敗条件を再現し、テストと実装の問題でないことを示す。

### 命名

- 検証する条件と期待結果を名前で表す
- 正常系・異常系をprefixで区別する
  - テストケースを関数で書く言語（Rust等）は`positive`・`negative`をprefixにする
  - テストケース名を文字列で書く言語（Go・TypeScript等）は`[positive] `・`[negative] `をprefixにする
    - prefixの後は「AがBのときCになる」の形で入力条件と期待結果を書く

### 構造

- テストの本体は次のパターンで書く
  - ユニットテストはArrange・Act・Assertパターン
  - ユニットテスト以外のテストはGiven-When-Thenパターン
- パターンの各節は空行で区切る
  - 空行で区切りを明確にできない場合のみ、各節にラベルを付ける
- BDD（Behavior Driven Development）スタイル（`describe`・`it`等）では、テスト対象の関数ごとに`describe`を分ける
- テーブルドリブンテストでは、テスト対象の関数ごとにテスト関数を分ける
  - ケースの構造体に、他のフィールドから導出できるフィールドを置かない
    - 期待するエラーのフィールドと「失敗するか」の真偽値を併置しない
    - 本番コードがエラーの種別を検査できない形の場合は例外とする
  - 1つの概念を複数のフィールドに分割しない
    - テストダブルが返す結果は、テストダブルの結果型のまま1つのフィールドに置く
- テスト側の共通化で重複を解消しない
  - 同じ定義が複数箇所にあることが原因なら、定義側で共通化する

### 検証

- 比較は完全一致を既定とする
  - 部分一致・緩い比較にする場合は理由を示す
  - 正常系は期待値全体を1つ組み立て、結果全体と比較する
  - フィールドごとに検証しない
- 異常系はエラーの型・種別まで検証する
  - エラーメッセージの文言は検証しない

### テストツール

- アサーション・モック・カバレッジ計測のツールは、プロジェクトの既存慣行に従う
  - 既存慣行が無い場合はreferenceに記載したツールを使う
- 同じ目的（値の比較・エラーの検査等）に複数のツールを使わない
  - 目的が異なるツールの併用（深い比較と単純な値の比較等）は例外とする
  - 既存の混在の統一が依頼範囲を超える場合は指摘に留める

### テストダブル

- テストダブルは、プログラム外部へのアクセス（ネットワーク・DB・時刻・乱数・外部コマンド・ファイルシステム等）にのみ使う
  - 内部モジュール同士は実物を使う
  - プログラム外部へのアクセスを差し替えられない場合は、差し替え可能にする設計変更を行なう
    - 設計変更が依頼範囲を超える場合は指摘に留める
- 呼び出しを記録するテストダブルの記録は、全件・順序込みで期待値と比較する
  - 引数に加え、プログラム外部へ渡す入力（標準入力・リクエストボディ等）も比較する
  - 途中で失敗する異常系は、失敗するまでの呼び出し列を期待値にする

### カバレッジ

- C1カバレッジを満たすよう依頼された場合は、次の順で進める
  1. 対象関数の条件分岐を列挙する
  2. 各分岐の真・偽を通すケースの有無を対応表にし、応答内に示す
     - 対応表はファイルに残さない
  3. 不足しているケースを追加する
  4. 到達不能・防御的な分岐は、理由を添えて対象外とする
  5. 追加したケースが機能することを、mutation testingで確認する
- C1カバレッジを機械計測できない言語・ランナーの場合は、上の手順に従って担保する
- C0カバレッジの数値を目標にしない
  - サブエージェント等にカバレッジの数値表を渡して、数値の改善を指示しない
- カバレッジの数値を上げるために、呼ばれたことだけを検証するテスト・期待値を実装から写したテストを追加しない

### mutation testing

既存テストの書き方を変えた場合・C1のためにケースを追加した場合は、mutation testingで検証が機能することを確認する。

- カバレッジを検証が機能することの根拠にしない
  - アサーションを削除しても実行される本番コードの文・分岐は変わらないため、カバレッジは変わらない
- 本番コードに誤りを1つずつ入れ、対象のテストが失敗することを確認する
  - 誤りは分岐条件の反転・定数の書き換え・コレクションの要素の削除・早期returnの無効化から選ぶ
  - 確認後は誤りを元に戻し、テストが成功することを確認する
- 安全に関わる検査（許可した範囲外への書き込み・権限・入力の検証）は、検査そのものを無効化してテストが失敗することを確認する
  - 実行環境が検査の無効化をブロックした場合は、確認できなかった検査を報告する
