# 子Agentプロンプトテンプレート

Step 3で子Agentを起動するときのプロンプト構造。`<>`のプレースホルダを埋めて使う。

## briefの原則

- **自己完結。** 子は親の会話を一切見ない。プロンプト単体で、課題・必要文脈・制約・成果物形式が完結していること。「さっき話したとおり」のような会話参照を含めない。
- **最終メッセージがそのまま報告物。** 子にはその前提を明示し、前置き・経過の語りを省かせる。
- **前提は一次確認してから書く。** 言語規約・既存パターン・品質ゲートのプレースホルダには、実物を見て確認した事実だけを記入する（不変則6）。

## 起動プロンプト

```text
<プロジェクト名>のタスク <ID>「<タスク名>」を実装してください。

## 作業環境（厳守）

- 作業ディレクトリ: <workspace絶対パス>
  これは<jj workspace / git worktree>の作業コピーです。すべての読み書き・ビルド・テスト実行はこのディレクトリ内で行ってください。
- <本体リポジトリ絶対パス> には一切触れないでください（読み取りも禁止）。
- VCS操作は読み取り系（status・log・diff・show）のみ許可します。<jjの場合: jjコマンドには必ず--ignore-working-copyを付けてください。>変更系（commit・branch・checkout・rebase・merge・push等）は一切実行しないでください。統合とコミットは呼び出し元が行います。変更は作業コピーに残したままにしてください。
- CLIツールが不足しても導入せず、報告して停止してください。
- <環境固有のhook制約。例: Bashコマンドを&&・||・;で連結しない（例外は先頭のcd <dir> && 1回のみ）>

## 言語規約

- <コメント・docコメント・ドキュメントの言語。実物で確認した事実のみ。例: コード内のコメント・docコメントは英語、design docは日本語>

## 事前に必ず読むもの

- <design doc等の該当節（タスクリストの「参照」から転記）>
- <既存コード（ファイル列挙）> — 既存のパターン・命名・エラー型の文体に合わせてください。

## タスク内容

<タスクリストから仕様の箇条書きと受け入れ条件を転記>

## 実装方針

- <確立済みパターンへの追従指示。例: monitor.rsの純粋状態機械パターンに合わせる>
- ドキュメントに無い仕様を発明しないでください。スコープ外の改善をしないでください。
- 並行実装中の他タスクの機能を先取りしないでください。統合点は最小限のインターフェースに留めてください。
- 新規依存の追加は最小限にし、追加した場合は理由を報告してください。
- <テスト方針の指示（テスト方針を定めたスキル・ドキュメントが環境にある場合のみ）。例: テストを書く前に Skill ツールで test-writing スキルをロードし、その方針に従ってください>

## 品質ゲート（全通過が完了条件）

- <プロジェクトの実コマンドを列挙。例: cargo fmt --check / cargo clippy --all-targets（warningゼロ）/ cargo test>

## 報告

あなたの最終メッセージがそのまま報告物になります。前置き・経過の語りは不要で、次の内容だけを書いてください。

- 実装内容: モジュール構成・公開API・既定値とその根拠
- 設計判断ごとの出典（file:line、design docの該当節、公式ドキュメントのURL）。出典の無い主張は事実として書かず、確認した事実と推測を区別して、推測にはその根拠を添えてください。
- 品質ゲートの実行結果
- 未解決の懸念
```

## 記入時の注意

- **作業ディレクトリは絶対パスで書く。** 相対パスは子のcwd次第でずれる。
- **hook制約は起動環境のものを転記する。** 親がhook拒否で学んだ制約は、子も同じhook下で動くため最初から焼き込む。
- **「事前に必ず読むもの」は具体的なファイル・節を列挙する。** 「関連コードを読んで」のような曖昧指示は読み漏れを生む。
- **並行起動時は全員に同じ確立パターン・規約を渡す。** それでも相互のコードは見えないため、方式・命名の食い違いは残り得る。統一は親の責務（Step 4）。
- **外部CLI経由の子にも同じbriefを渡す。** 渡し方・実行上の注意はmodel-selectionスキルに従う。

## 修正指示の定型（SendMessage）

修正が出たら、新規Agentを立てず同一Agentへ送る。起点はユーザーレビュー（Step 5）の場合と、親による並行タスク間の突き合わせ（Step 4）の場合がある。毎回次を含める。

```text
<修正の起点。例: ユーザーレビューで修正指示が出ました / 並行タスクとの方式統一のため修正を依頼します>

<修正内容の具体的指示>

制約の再掲:
- 作業ディレクトリは <workspace絶対パス> のみ。本体リポジトリには触れない。
- VCS操作は読み取り系のみ。変更系は一切実行しない。

現在の状態: <親が把握している状態。例: 変更は統合前>

完了したら修正内容と品質ゲートの再実行結果を報告してください。
```
