# Orchestrator

親（コーディネータ）がタスクを子Agentへ委譲し、jj workspace / git worktreeで分離して実装させ、独立検証・人間レビューを経て統合する。

## 概要

分解済みタスクリストを入力に、親は「タスク選定 → workspace作成 → 子Agent起動 → 独立検証 → 統合前レビュー → 統合 → 後処理」のサイクルを回す。子は割り当てられたworkspace内での実装と報告だけを行い、変更系のVCS操作・統合・コミットは親が一元的に担う。

このパターンの核はコンテキスト分離にある。ユーザーと対話する親は実装せずレビュー・検証・統合に徹するため、実装過程の試行錯誤や合理化がレビューの視点に混ざらない。この利得は並行性が無くても成立するので、逐次でしか進められないタスク列や単一タスクの実装にも適用してよい。

## Requirements

外部ツールが欠けていれば停止し、ユーザーへエスカレーションする（Agentは外部ツールを導入しない）。

### 外部ツール

| ツール | バージョン要件 |
| --- | --- |
| jj または git | jj: `jj workspace`サブコマンドを持つこと（動作確認: 0.43.0）/ git: `git worktree`サブコマンドを持つこと |

リポジトリルートに`.jj`があればjjを使い（colocated含む）、無ければ`.git`のgitを使う。存在確認コマンドを次に示す（使う側のみ確認すればよい）。

```sh
command -v jj >/dev/null 2>&1 || { echo "jj not found." >&2; exit 1; }
```

```sh
command -v git >/dev/null 2>&1 || { echo "git not found." >&2; exit 1; }
```

### 連携スキル

| スキル | 用途 |
| --- | --- |
| task-decomposition | タスクリストの作成・見直し |
| model-selection | 子モデルの選定 |

使う場面で利用可能スキル一覧に無ければ、代替せず停止してユーザーへエスカレーションする。

### ハーネス機能

ハーネスに次の機能を前提とする。欠ける場合はこのスキルを適用せず、その旨をユーザーへ報告する。

- サブエージェントの起動（モデル指定・バックグラウンド実行・完了通知）
- 完了済みサブエージェントへの追加指示送信（SendMessage相当。コンテキストを保持したまま修正を依頼するため）

## 不変則

ワークフロー全体を通じて次を厳守する。

1. **子は変更系のVCS操作をしない**（commit・branch・checkout・rebase・merge・push等）。読み取り系（status・log・diff・show）は許可する。ただしjjでは読み取り系コマンドもsnapshotを伴うため、子には必ず`--ignore-working-copy`を付けさせる（親のsnapshot管理との干渉と、署名等の対話承認でのブロックを避ける）。統合・コミットは親のみが行う。
2. **人間の承認なしに統合しない。** 統合前レビュー（Step 5）は省略できない。
3. **子の報告は二次情報。** 品質ゲートは親が独立に再実行し、差分は親が自分で点検する。
4. **完了した子Agentは破棄せず保持する。** 修正は同一AgentへSendMessageで指示する（新規Agentを立てない）。
5. **タスク状態はタスクリストへ随時反映する。** 親のcontextやcompaction要約をタスク状態の唯一の担体にしない。
6. **子プロンプトは自己完結させ、書く前提は一次確認してから書く。** 子は親の会話を一切見ない。プロンプト単体で課題・必要文脈・制約・成果物形式が完結すること。既存コードの規約・スタイル・言語は、実物を見て確認した事実のみを記す。

## 前提条件の確認（開始時）

1. **タスクリストの有無。** 無ければtask-decompositionスキルをロードして分解し、ユーザーの承認を得てから進む。タスクリストの入力契約は、(a) タスクID、(b) 子が推測で埋めずに済む自己完結の仕様と参照、(c) 依存関係、(d) 完了マークを更新できる形式、の4点で、これを満たせば出所は問わない（形式はtask-decompositionスキルの定義に従う）。
2. **VCSの判定。** リポジトリルートに`.jj`があればjj、無ければ`.git`のgitを使う。どちらも無ければ停止してユーザーへ確認する。
3. **`.tmp/`がignoreされていること。** workspaceを`.tmp/`配下に置くための前提条件。次のprobe方式で確認する。

   ```sh
   mkdir -p .tmp/agent-workspaces
   ```

   ```sh
   touch .tmp/agent-workspaces/.probe
   ```

   status（jjは`jj st`、gitは`git status --porcelain`）の出力に`.tmp/`配下のファイルが現れなければignoreされている（jjでsnapshotに対話承認が必要な環境では、`jj st`もバックグラウンド実行してユーザーへ承認を依頼する）。現れた場合はprobeを削除し、進行を停止してユーザーへエスカレーションする（`.tmp/`のignore設定、または配置先の変更を確認する）。確認後はprobeを削除する。

## ワークフロー

### Step 1: タスク選定

- タスクリストの依存グラフから、未完了かつ依存元がすべて完了したタスクを列挙する。
- 並行候補には「互いに素」の判定を実ファイルレベルで行う。各タスクが触るファイル・モジュールを予測し、集約ファイル（設定スキーマ・エラー型・mod宣言・依存マニフェスト等）はモジュール分割の見た目に反して交わりに入りやすいため、明示的に予測へ含める。
- 変更ファイル集合が交わる見込みのタスクは、(a) 並行せず逐次にする、(b) 統合点を最小限のインターフェースに絞って並行し、統合時の競合解消を親が引き受ける、のどちらかを明示的に選ぶ。
- 並行可能なタスクが複数あるときは、着手構成（どれを並行するか）をユーザーに提示して確認する。

### Step 2: workspace作成

統合済み先端`<base>`から、タスクごとに作業コピーを`.tmp/agent-workspaces/<タスクID>/`に切る。`<base>`は直前の統合コミット（統合をまだ行っていなければ開始時点の先端）で、log等で確認してから使う。

```sh
jj workspace add --name <タスクID> -r <base> .tmp/agent-workspaces/<タスクID>
```

```sh
git worktree add -b agent/<タスクID> .tmp/agent-workspaces/<タスクID> <base>
```

`.tmp/`配下に置くのは、ユーザーが手元のエディタでそのまま実装内容を確認できるようにするため。gitignoreされたディレクトリ内のネストworkspace / worktreeは、本体作業コピーのstatus・snapshotに混入しない。

jjでsnapshotを伴う操作が署名等の対話承認でブロックされる環境では、該当操作をバックグラウンド実行してユーザーへ承認を依頼し、読み取り系は`--ignore-working-copy`を付けて実行する。

コードを変更しないタスク（調査・スパイク等）はworkspaceを作らず、本体リポジトリを読み取り専用で参照させてよい（プロンプトの作業環境節をそれに合わせて調整する）。

### Step 3: 子Agent起動

- モデルはmodel-selectionスキルをロードして選ぶ。ユーザー指定があればそれに従う。
- 起動は起動元ハーネスのサブエージェント機構を優先し、汎用のエージェント種別（Claude Codeなら`subagent_type: "general-purpose"`）でバックグラウンド実行する。ハーネスから起動できないモデルは外部CLI経由とし、その実行上の注意はmodel-selectionスキルに従う。
- プロンプトは[references/subagent-prompt.md](references/subagent-prompt.md)のテンプレートを埋めて作る。プレースホルダの前提（言語規約・既存パターン・品質ゲートコマンド）は一次確認してから記入する（不変則6）。
- 並行起動は互いに素が確定したタスクのみ。複数の起動は同一メッセージ内の並列tool useで行う。

### Step 4: 完了後の独立検証（親）

子の完了通知を受けたら、報告を鵜呑みにせず親が検証する。

- 検証ゲート: まず完了通知の内容が実質的な報告か確認する。ステータス行・エラーダンプ・空応答は成果ではない。実質が無ければ再実行を指示し、再度失敗したらユーザーへ報告する。
- 変更点検: 作業コピーの差分を列挙し、各ファイルを点検する（手順は[references/integration.md](references/integration.md)。jjでは親がtaskワークスペース内でsnapshotを実行しない限り作業コミットが空のままになる点に注意）。
- 品質ゲート（fmt・lint・test等、プロジェクト規約から親が確定したコマンド）をworkspace内で親が再実行する。
- 指示遵守の確認が必要なら、子の出力ファイル・transcriptを確認する（例: 指定スキルをロードしたか。ハーネスが参照手段を提供しない場合は省略する）。
- 並行タスクが複数完了しているときは、相互のコードが見えないまま実装された方式・命名の食い違い（デシリアライズ方式・エラーバリアント命名等）を親が突き合わせ、揃える側を決めてSendMessageで修正指示する。修正後は本Stepの検証をやり直す。

### Step 5: 統合前レビュー（人間ゲート）

検証を通過したら、統合せずユーザーへ報告し承認を待つ。

- 報告内容: 変更規模・モジュール構成・公開API・設計判断とその根拠（出典付き）・品質ゲート結果・親自身の点検で気づいた懸念。
- 設計上の選択肢が生じたら、選択式の質問インターフェースで提示する。
- ユーザーは`.tmp/agent-workspaces/<タスクID>/`を手元のエディタでそのまま確認できる。
- 親のレビューから独立した第三者視点が必要なら、設計意図・経緯を渡さないフラットな臨時レビューAgentを起動する（環境に独立レビュー用のスキルがあればそれを使う）。
- ユーザーがworkspace内を直接手修正した場合は、統合時に親が差分を点検してから統合に進む（手順は[references/integration.md](references/integration.md)）。
- 修正指示が出たら、同一AgentへSendMessageで指示する（不変則4）。メッセージには作業ディレクトリ厳守・VCS制約の再掲と、現在の状態を毎回含める。修正完了後はStep 4からやり直す。

### Step 6: 統合（承認後、親のみ）

[references/integration.md](references/integration.md)のVCS別手順に従う。

- 単独タスク: 作業コミットへコミットメッセージを付けて本体へ取り込む（jj: `jj describe`→`jj new`。taskワークスペース内で`jj commit`としてもよい / git: worktree内でcommit→本体で`git merge --ff-only`）。
- 並行タスク: 線形化（rebase）→競合は親が手動解消→統合ツリーで品質ゲートを再実行→取り込み。
- コミットメッセージはプロジェクトの規約に従い、親が統合時に付与する（子には委ねない）。

### Step 7: 後処理

1. **タスクリスト更新**: 完了したタスクに完了マークを付ける（不変則5。状態の外部化）。
2. **workspace cleanup**: 統合が完了・検証済みなら、ユーザーの指示を待たずに[references/integration.md](references/integration.md)のcleanup手順でworkspaceを撤去する。Agent自体は保持する（不変則4。後からの修正指示をコンテキスト付きで受けられるようにする）。
3. **タスクリスト見直し**: 調査タスクの完了後や、残タスクの前提が変わる発見があったときは、task-decompositionスキルの「反復的な分解」に従い残タスクを見直す（大きな再定義はユーザー承認）。
4. 残タスクがあればStep 1へ戻る。全タスク完了なら、その旨をユーザーへ報告して止まる（push・PR作成は指示があった場合のみ）。

## context管理

- タスクリストに載っているタスクの状態を常に正しいものとして扱い、実態が変わったら直ちにタスクリストへ反映する。ワークフローの進め方は常に本スキルの記載に従い、親のcontextやcompaction要約を規約の置き場にしない。compactionのタイミングは規定しない（必要ならユーザーが判断する）。
- compaction後に作業を再開するときは、本スキルを再読み込みし、タスクリストとlogで状態を再確認してから次タスクに着手する。compaction要約中の規約・前提が本スキル・タスクリスト・実物と食い違う場合は、要約でなく後者に従う。
