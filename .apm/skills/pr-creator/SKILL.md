# Pull Requestの作成

GitHub・GitLabのPull Request（GitLabではMerge Request）を、次の方針で作成する。

- 本文には、何を変更したか（What）・なぜ変更したか（Why）・どんな影響が出るか（Impact）を書く
- 途中でどんな問題が起き、どう解決したかの経緯（試行錯誤・撤回した実装・デバッグ過程）は書かない。PR本文の読み手が必要とする情報は、変更前後の差分であるためである
- 差分・コード・ユーザー入力から得られない情報は書かない。「おそらく」「たぶん」で埋めず、不確実な点は`[要確認]`を付けてユーザーへ提示する
- ユーザーへ質問する前に、コミット差分・変更ファイル・コミットメッセージ・関連コードから埋められる項目を埋める
- 変更の動機・背景・レビュー時の注意点・破壊的変更の意図の有無・優先度等、差分から読めない情報はユーザーに確認する。質問は1回にまとめる
- ドラフトをユーザーが承認したら、追加確認（ラベル・ベースブランチ等）を挟まず作成まで進め、結果のURLを報告する

## 準備

git（2.0以上）がない場合は、作業を止めてユーザーに確認する。
GitHubのリポジトリでは`gh`（2.0以上）、GitLabのリポジトリでは`glab`（1.0以上）がない場合も、作業を止めてユーザーに確認する。
本文が日本語の場合に検査で使う`ja-writing`スキルがない場合も、作業を止めてユーザーに確認する。
外部ツールを自分でインストールしない。

## 手順

### 1. プラットフォームを判定する

リモートのURLを取得する。

```bash
git remote get-url origin
```

リモートのURLからプラットフォームを判定する。

- `github.com`を含む場合は、GitHub（`gh` CLI）とする
- `gitlab.`を含む場合（ホストは問わない）は、GitLab（`glab` CLI）とする
- それ以外の場合は、ユーザーにプラットフォームを確認する

CLIの使い方とプラットフォーム固有の差異は[references/platform-detection.md](references/platform-detection.md)を参照する。

### 2. ベースブランチとheadを確定する

マージ先のブランチ（base。通常は`main`）と、マージ元のブランチ（jjの場合はchange）（head）を確定する。
不明な場合は、デフォルトブランチをbaseとして提示し、ユーザーに確認する。

### 3. 差分を把握する

リポジトリルートに`.jj`があれば`jj`、なければ`git`で差分とコミット履歴を取得する。

```bash
# jjで管理しているリポジトリ
jj log -r "main..@"          # コミット一覧
jj diff -r "main..@"         # 累積差分

# gitで管理しているリポジトリ
git log --oneline main..HEAD
git diff main...HEAD
```

コミットメッセージから変更の意図を読み取る。
変更したファイルから影響範囲を推定する。

### 4. PRテンプレートを選ぶ

プロジェクトのPRテンプレートを、同梱のテンプレートより優先する。

GitHubでは次のファイルを確認する。

- `.github/PULL_REQUEST_TEMPLATE.md`
- `.github/PULL_REQUEST_TEMPLATE/*.md`（複数テンプレート）
- `.github/pull_request_template.md`

GitLabでは次のファイルを確認する。

- `.gitlab/merge_request_templates/*.md`

複数のテンプレートが該当する場合は、変更内容に最も合うものを選ぶ。
迷う場合は、ユーザーに確認する。
プロジェクトのテンプレートがない場合は、同梱の[templates/default.md](templates/default.md)を使う。

選んだテンプレートは、ドラフトを書く前に全文を読む。
記憶にある典型的なPRテンプレートの構成でドラフトを書かない。
見出し・順序・各節の規則を抽出し、ドラフトに厳密に反映する。
節の省略・追加・改名・並べ替えはしない。

### 5. 不足している情報をユーザーに質問する

テンプレートの節ごとに、差分から埋まるか・ユーザーが既に提供したか・質問する必要があるかを判定する。

差分・コードから埋める項目を次に示す。

- 変更内容（What）
- 影響範囲（変更したファイル・公開APIの変化から判定する）
- 関連Issue（コミットメッセージの`#123`・`Closes #123`から取得する）

差分から読めないため、ユーザーに質問する項目を次に示す。

- 変更の動機・背景（Why）
- レビュー時に特に見てほしい点
- 破壊的変更・移行手順を伴うことを意図したか

質問は1回にまとめて提示する。

### 6. 本文のドラフトを書く

選んだテンプレートに沿って、収集した情報から本文を作成する。

- What・Why・Impactを差分に基づいて記述する
- 途中の経緯（「最初はAを試したがダメでBにした」「デバッグでCに気づいた」等）は本文に含めない。最終的な変更内容・理由・影響だけを書く
- エラーメッセージ・コマンド・コードは、言語ヒント付きのフェンスで囲む
- トークン・認証情報・内部ホスト名・個人パスは、`[TOKEN]`・`[INTERNAL_HOST]`等のプレースホルダーに置換する
- 本文の言語は、リポジトリで既存のPR・Issueに使われている言語に合わせる。不明な場合は、ユーザーの入力言語に合わせる

タイトルは、Conventional Commitsの形式で変更の要点を1行で書く。
1行で表現できない場合・抽象的になりすぎる場合は、PRのスコープが過大であるため、ユーザーにPRの分割を提案する。

### 7. 日本語の本文をja-writingで検査する

本文が日本語の場合は、ドラフトを提示する前に`ja-writing`スキルで本文を検査する。
承認の対象を検査後の本文にするため、承認後に本文は変わらない。

1. `ja-writing`が定める一時ファイルのディレクトリに、本文をMarkdownファイルとして書き出す。
   このファイルを手順8の本文ファイルとして使う
2. `ja-writing`の手順（textlintによる検査とAIレビュー）に従って、本文を修正する
3. textlintの`warning`・AIレビューの指摘を反映しなかった場合は、その指摘と理由を手順8の確認に含める

本文が日本語でない場合は、この手順を省略する。

### 8. ユーザーの承認を得てPRを作成する

ドラフトは1回だけ提示する。
提示するドラフトには、ユーザーの判断に必要な情報を全て含める。

> 以下の内容でPRを作成する。問題なければ「OK」、修正が必要なら指摘してほしい。
>
> - base: main ← head: feature/xxx
> - タイトル: TITLE
> - ラベル: [一覧、なしなら「なし」]
>
> ---
> (本文)

承認（「OK」「はい」等）の後は、追加の質問・確認を挟まず次の処理を続けて実行する。

1. 本文を一時ファイル（`/tmp/pr-body.md`等）に書く。手順7で本文ファイルを書き出した場合は、そのファイルを使う
2. 作成コマンドを実行する
3. URLを報告する

GitHubでは次のコマンドを使う。

```bash
gh pr create \
  --base main \
  --head feature/xxx \
  --title "TITLE" \
  --body-file /tmp/pr-body.md \
  --label "enhancement"   # 該当する場合
```

GitLabでは次のコマンドを使う。

```bash
glab mr create \
  --source-branch feature/xxx \
  --target-branch main \
  --title "TITLE" \
  --description "$(cat /tmp/pr-body.md)" \
  --label "enhancement"   # 該当する場合
```

本文は、インラインの`--body`ではなく、GitHubでは`--body-file`、GitLabではファイル経由で渡す。
本文の改行・記号が、シェルのエスケープで崩れる問題を避けるためである。

ユーザーが修正を依頼した場合は、修正を反映し、日本語の本文を手順7と同じ方法で再び検査する。
その後、再び1回の確認の形式でドラフトを提示する。

## 禁止事項

このスキルで禁止する操作を次に示す。

- 途中の経緯（「最初はXしたがダメでYにした」「デバッグでZと判明」）を本文に書く
- 差分から読めない変更理由・影響を捏造する
- テンプレートの見出しを改変・省略・追加・並べ替えする
- ユーザーの承認前にPRを作成する
- 日本語のドラフトを`ja-writing`で検査せずにユーザーへ提示する
- 1行で表現できない巨大なPRをそのまま作成する（スコープが過大であるとして分割を提案する）
- 承認後に、ラベル等の追加確認のために作成を止める
- 外部ツールを自分でインストールする

## 例

### 例1: バグ修正のPR

1. `git remote get-url origin`を実行する → GitHubの`acme/web`
2. baseを`main`、headを現在のブランチに確定する
3. `jj diff -r "main..@"`で差分を把握する → `src/auth.ts`にnullチェックを追加した変更と判明する
4. `.github/PULL_REQUEST_TEMPLATE.md`を確認する → テンプレートが存在しないため、`templates/default.md`の全文を読む
5. ユーザーに、この変更の動機（報告されたバグの修正・自発的な修正のどちらであるか）と、レビューで特に見てほしい点を質問する
6. What（nullチェックの追加）・Why（ユーザーの回答）・Impact（影響は認証フローのみ、破壊的変更なし）でドラフトを書く。途中の経緯は書かない。日本語の本文を`ja-writing`で検査する
7. base・head・タイトル・ラベル・本文を1回で提示する →「OK」→ `gh pr create`を実行する → URLを報告する

### 例2: リファクタリングのPR

1. GitLabと判定する
2. `jj log -r "main..@"`で複数のコミットの意図を読む
3. プロジェクトの`.gitlab/merge_request_templates/refactor.md`を優先して選び、全文を読む
4. 影響範囲（公開APIの変化の有無）を差分から確認する
5. ユーザーに動機（保守性・性能のどちらが主な目的か）を確認する
6. テンプレートの見出しに厳密に従ってドラフトを書く。日本語の本文を`ja-writing`で検査する
7. 1回で確認する → 承認 → `glab mr create`を実行する → URLを報告する
