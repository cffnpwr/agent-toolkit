# 改善提案テンプレート

既存の機能を強化する（性能・UX・コード品質）場合に使う。

プロジェクトに`.github/ISSUE_TEMPLATE/enhancement*.md`等のテンプレートがあれば、そちらを優先する。

```markdown
## 概要
[改善したい内容を1行で]

## 現在の動作
[現状の動作（コードベースから読み取れる内容で記述）]

## 不十分な点
[現状の何が問題か（動作はするが何が不十分か）]

## 望ましい動作
[改善後にどうあるべきか]

## 定量的な目標
[定量的な目標があれば記載（例: 「ロード時間を3秒から1秒に」「メモリ使用量を50%削減」）]

## 影響範囲
[改善が影響する範囲（ファイルパス・機能名）]
- `path/to/file.ts`

## 動機
[今これを改善する理由（ユーザー体験・保守性・パフォーマンス問題等）]

## 受け入れ条件
- [ ] [完了条件1]
- [ ] [完了条件2]

## 検討した代替案
[他のアプローチと、これを選んだ理由（なければ節ごと削除）]

## 補足情報
[関連Issue・ベンチマーク結果・参考資料等]
```

## 節の規則

各節の規則を次に示す。

- 現在の動作には、コードベースから読み取れる事実を書く。ユーザーの主観は次の節に分ける
- 不十分な点には、ユーザー視点の不満（「遅い」「分かりにくい」「保守しづらい」等）を書く
- 望ましい動作には、改善後の状態を書く。実装方法は書かない（実装方法はPRで議論する）
- 定量的な目標が該当しない場合は、節ごと削除する。無理に数値化しない
- 動機には、優先度の根拠になる動機を書く。バグではないため、「直したいから」では根拠として弱い
